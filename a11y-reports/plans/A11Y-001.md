# A11Y-001: Primary CTA buttons are focusable but perform no action

- Severity: High
- Source report: [report.md](../report.md)
- Affected URL or flow: `http://127.0.0.1:5173/`, CTA activation
- Affected viewport(s): Desktop `1440x900`, mobile `390x844`
- Representative location(s): Header `Book a call`, hero `Start a sprint`, hero `View services`, pricing `Request proposal`
- Code location(s): `src/App.tsx` lines 69, 88, 92, and 198
- Evidence: `screenshots/desktop-start-sprint-focus-annotated.png`, `screenshots/mobile-view-services-focus-annotated.png`

## Problem

The page exposes several visible, focusable CTA buttons, but activating them with keyboard or pointer produces no meaningful result. `View services` appears to be section navigation but is implemented as a button without a target. `Book a call`, `Start a sprint`, and `Request proposal` appear to start conversion flows but do not navigate, open a dialog, submit a form, or provide feedback.

## Impact

Keyboard and assistive-technology users can reach and activate the controls but receive no confirmation, destination, or recovery path. This makes the page's primary conversion task appear broken and can leave users repeatedly activating controls without understanding what happened.

## Success Criteria

- [ ] `View services` is implemented as a real link to `#services`, or as a button with equivalent scripted navigation and correct focus behavior.
- [ ] `Book a call`, `Start a sprint`, and `Request proposal` each have a defined accessible result: route, link, form, modal, or clearly disabled/unavailable state.
- [ ] If a modal is used, it has an accessible name, traps focus while open, closes with Escape, and restores focus to the triggering CTA.
- [ ] The affected task can be completed with keyboard only where keyboard access is expected.
- [ ] The element or pattern exposes the correct accessible name, role, state, and relationship where applicable.
- [ ] The fix works at desktop `1440x900` and mobile `390x844`.
- [ ] The change does not remove existing pointer, keyboard, form, or responsive behavior.
- [ ] A focused regression check exists when the codebase has a practical place for it.

## Verification Steps

- [ ] Reproduce the original issue from the source report before changing code.
- [ ] Decide the intended behavior for each CTA and implement it in the smallest relevant component or page surface.
- [ ] Re-test each CTA with Tab and Enter.
- [ ] Re-test each CTA with pointer click.
- [ ] Confirm that URL changes, focus movement, modal opening, or feedback matches the visible CTA label.
- [ ] Re-test desktop `1440x900` and mobile `390x844`.
- [ ] Re-run axe or the project's accessibility checks when available, and confirm the manual issue is resolved.

## Notes

- Prefer native anchors for navigation targets. Use buttons only for in-page actions that do not navigate.
- Preserve unrelated UI styling unless it directly contributes to the accessibility failure.
